# Roadmap: News Digest Bot (MVP)

Цель MVP: скрипт на VPS по cron собирает статьи из нескольких источников, LLM оценивает их с учётом профессионального профиля и интересов пользователя, в Telegram приходят только статьи с оценкой выше порога: ссылка + «почему интересно».

Стек: Python 3.11+, feedparser, httpx, SQLite, Telegram Bot API (HTTP, `sendMessage`), cron.

Правила для агента:
- После каждого подпункта запускай и проверяй результат, ставь галочку только когда критерий выполнен.
- Секреты только в `.env`, в git не коммитить.
- Не переходи к следующей фазе без завершения критериев текущей.
- Не принимай самостоятельно существенные архитектурные решения, не предусмотренные roadmap. Если обнаружена неоднозначность — задай вопрос.

## Общая логика работы (Pipeline)

1. **Сбор:** получение статей из настроенных источников (RSS/Atom, Hacker News, GitHub, Telegram и т.д.).
2. **Нормализация:** приведение полученных материалов к единому формату `Article`.
3. **Дедупликация:** проверка URL в SQLite. Если статья уже существует, повторно не добавлять.
4. **Получение полного текста:** если фид содержит только анонс, попытаться получить страницу через HTTP и извлечь текст с помощью `trafilatura`.
5. **Предварительная фильтрация:** отсечение заведомо нерелевантных материалов по ключевым словам и заголовкам.
6. **LLM-оценка:** передача текста статьи и профессионального профиля в LLM. Получение оценки релевантности, объяснения и возможной связи с интересами или проектами.
7. **Сохранение результата:** запись оценки и объяснения в SQLite.
8. **Отправка:** если оценка достигает порога, отправить статью в Telegram.
9. **Логирование:** фиксировать ошибки сбора, извлечения текста, оценки и отправки. Статьи с ошибками не теряются и могут обрабатываться повторно.

### Жизненный цикл статьи

Каждая статья идентифицируется уникальным URL (PRIMARY KEY в SQLite) и имеет статус обработки:

- `new` — статья собрана, текст доступен, ожидает LLM-оценки.
- `scored` — LLM оценила статью, результат сохранён в БД. Статус используется независимо от того, прошла статья порог отправки или нет.
- `sent` — статья успешно отправлена в Telegram.
- `error` — произошла ошибка обработки. Статья сохраняется и допускает повторную попытку.

Дополнительное поле `error_stage` позволяет определить этап ошибки (`fetch`, `score`, `send`).

Правила:
- Повторное обнаружение URL не создаёт дубликат.
- Ошибка не должна приводить к потере статьи.
- Повторная обработка ошибок выполняется при последующих запусках с учётом ограничений повторных попыток.
- Статья со статусом `scored`, не прошедшая порог, повторно не оценивается и не отправляется.
- Статья со статусом `scored`, прошедшая порог, но не отправленная из-за ошибки Telegram, должна иметь возможность повторной отправки.
- Статус `sent` устанавливается только после успешной отправки сообщения.

## Фаза 3. LLM-оценка

- [ ] 3.1 `profile.md`: шаблон профессионального профиля, который заполняю я. Он должен описывать:
  - Профессиональный опыт и используемый стек (1С, BSL, Python и т.д.).
  - Текущие проекты и направления работы (ИИ-конвейер разработки, SDD, автотесты 1С и т.д.).
  - Интересы, цели и направления развития.
  - Что НЕ интересно (общие новости про ИИ без практики, маркетинг, хайп).
  
  Важно: перечисленные проекты и технологии — контекст для понимания интересов, а не закрытый список допустимых тем. LLM должна самостоятельно выявлять смежные технологии, неожиданные применения, новые подходы и потенциально полезные направления, даже если они напрямую не связаны с текущими проектами.

- [ ] 3.2 `scorer.py`: вызов LLM через OpenAI-совместимый endpoint (`LLM_BASE_URL`, чтобы можно было работать и через LiteLLM); вход — заголовок + полный текст + профиль; выход — строгий JSON `{score: 0-10, reason: "...", project: "..."}`.
  
  LLM должна оценивать потенциальную полезность статьи с учётом профессионального контекста пользователя, а не только совпадение с перечисленными технологиями и проектами. `reason` должен объяснять конкретную пользу статьи. `project` может указывать на текущий проект, направление интересов или потенциально новое применение. Прямая связь с существующим проектом не обязательна.

- [ ] 3.3 Парсинг ответа с защитой: невалидный JSON → одна повторная попытка → иначе статья помечается ошибкой и не отправляется
- [ ] 3.4 Грубый предфильтр по ключевым словам/заголовку до вызова LLM (экономия токенов); список слов в `sources.yaml`
- [ ] 3.5 Отправка только при `score >= SCORE_THRESHOLD` (по умолчанию 7), порог переопределяется на уровне источника
- [ ] 3.6 Формат сообщения:
  ```
  🔥 8/10 · Название
  Почему интересно: <1–2 предложения с объяснением потенциальной пользы>
  <ссылка>
  ```
- [ ] 3.7 Все оценки (в т.ч. неотправленные) пишутся в БД для последующей настройки порога
- [ ] 3.8 Модель и fallback-список задаются в `.env` (`LLM_MODEL`, `LLM_FALLBACK_MODELS`); в запросе передаётся массив `models` OpenRouter, ID моделей в коде не зашиты
- [ ] 3.9 Лимитер: пауза ≥3 с между LLM-вызовами; дневной счётчик запросов в БД с потолком `LLM_DAILY_LIMIT` (по умолчанию 900); при достижении потолка оценка останавливается до следующих суток, статьи остаются в очереди
- [ ] 3.10 Обработка ошибок: 429 → пауза и повтор позже, 402 → остановка оценки + уведомление в Telegram, 5xx/пропавшая модель → следующая из fallback
- [ ] 3.11 Не-JSON ответ не требует поддержки `response_format`: JSON извлекается из текста (поиск первого `{...}`), промпт требует «только JSON»
- [ ] **Готово, когда:** на прогоне по 30+ реальным статьям отправляются единицы, и в «почему интересно» объяснена конкретная потенциальная польза, включая смежные и неожиданные применения
